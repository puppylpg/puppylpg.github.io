# 将对话归档为文章

## 核心原则

**对话是素材，不是文章结构；主线是问题链，不是知识清单。**

**先呈现具体问题，再引出解决它的技术。** 介绍技术或设计时，先让读者理解实际场景中的目标、困难，以及原有做法的不足，再解释对应机制怎样解决问题、解决到什么程度。不要先罗列技术、组件或接口，再补充它们的用途。

**简洁，直说核心。** 开头用一两句话说清具体问题，随后直接解释。用短句和具体表达，删掉绕弯铺垫、反复设问、重复总结和没有信息量的过渡。只保留理解核心问题必需的背景、证据与边界，不为覆盖所有聊过的知识点而扩写。

解释代码或 API 时，优先用一个最小可运行示例贯穿输入、转换和输出，只对比影响当前问题的关键参数；其余细节给参考链接。简洁不能省掉必要因果，但一个例子已经讲清的内容，不再另写一套概念或参数百科。

最终读者没有参与对话，不知道谁问过什么、发生过哪些纠正。先从对话中提炼一个能够独立成立的主题，再把对话中的"为什么"重排成一条读者视角的问题链，按链成文。

最常见的失败模式：把对话覆盖的知识点当作待办清单，逐条写成章节。这样产出的是面向提问者的总结，不是科普文——每节的存在理由是"对话里讲过"，而不是"读者读到这里必然想问"。零上下文读者没有那些背景，看到的是一堆突兀、互不关联的块。

禁止：

- 按聊天时间线复述"先问了什么、后来又补充什么"；
- 把用户的问题逐条改成标题，形成隐性的 FAQ；
- 使用"你问到""前面回答过""真正的问题是"等依赖聊天上下文的表达；
- 把追问答案和纠错内容直接追加到文章末尾。

## 工作流程

### 1. 提炼主题与问题链素材

回顾完整对话，先确定：

- 一句话主题：文章最终解释什么对象或解决什么认知问题；
- 读者起点：零上下文读者已经知道什么，还缺哪些前置概念；
- 概念依赖：哪些对象、关系和背景必须先介绍；
- 问题链素材：对话中的哪些"为什么"和追问构成了认知推进，各自依赖什么前置概念；
- 技术的引入理由：每项技术对应哪个具体困难，原有做法在哪里增加成本或无法满足需求；
- 关键素材：值得保留的例子、公式、图、代码、反例和边界；
- 文章范围：最终内容是否已经超出对话最初的问题。

删除重复问答、过程性确认、已被后续纠正的旧说法和仅对聊天参与者有意义的内容。对话里讲过但主线不需要的内容同样删除；确有参考价值时给链接，不默认追加文末 FAQ。

### 2. 先搭问题链，再定骨架

不要先列章节再填内容。先把全文压缩成一条问题链：

```text
场景/现象 → 读者必然产生的第一个疑问 → 回答 → 该回答引出的新疑问 → …… → 结论
```

技术说明中的链节应进一步落实为：具体场景与目标 → 遇到的困难或原有做法的负担 → 引入对应技术 → 解释解决机制与边界 → 新需求或尚未解决的问题。可以用同一个逐步发展的场景串联各节；不要为了套用结构，给非技术叙事编造痛点，或将教学上的因果关系写成未经核实的技术发展史。

规则：

- **每节服务核心问题。** 检查本节解决什么、依赖哪些前文；无法说明必要性就删掉。问题链用于理清因果，不要求每节都制造一个新疑问；核心问题解释清楚就收住。
- **知识按需引入。** 工具性概念（术语、分层、数据格式）不前置成"预备知识"章节——那是教科书思维。在第一个需要它的链节引入，概念才有存在理由，读者才知道为什么要学它。
- **问题先于方案，落实到正文顺序。** 正文中的技术介绍、结构图、接口示例和版本演进表应出现在对应困难已经建立之后，用来解释问题如何得到解决。只把标题改成问题，或在技术清单前加一句泛泛的“为了提高效率”，不算完成问题驱动的改写。
- **删除测试。** 某节删掉后文不会断裂，就说明它不在主线上。
- **链节定小节，相邻归大块。** 链节即小节（H3）；同属于一个论证阶段的相邻链节归并为一个大块（H2），每块开头用一句导语说明这块解决什么、和上一块的关系。平级 H2 超过约 6 个时，停下来归堆。
- 兜底顺序模板（场景→背景→例子→组件→机制→取舍→结论）只用于检查遗漏环节，**不能替代问题链校验**——模板排得通但问题链断掉的结构，仍然不合格。

写正文前检查每个小节：这一节为什么此时出现；它依赖的概念是否已经介绍；它为下一节建立了什么基础。

对话中的追问和纠正必须拆开，放回相应概念第一次需要它们的链节，改写成陈述式正文。

### 3. 写成独立、可读的科普文章

- 从具体场景、直觉冲突或读者能够感知的问题切入，不在开头直接宣布最终结论。
- 先用自然语言建立直觉，再给专业术语、公式或实现细节。
- 保留关键推理链和必要例子；不要为了缩短篇幅省略"为什么"。
- 公式使用本站兼容的行内 `$...$` 和块级 `$$...$$`，首次出现时解释符号与维度。
- 流程、层级、时序、架构和状态关系优先使用合适的 Mermaid 图；图必须承担解释任务。
- 引用外部资料时使用有意义的 Markdown 内联链接，优先引用官方或一手来源。
- 中文表达使用配对的弯引号""，避免翻译腔、套话和营销号标题。

标题应直接、可检索并覆盖全文范围。内部比较至少 3 个候选，优先选择最朴素准确的标题。

### 4. 写入博客

发布目录、分类、文件命名和 frontmatter 遵循根目录 `AGENTS.md`。未指定时写入 `_ai/`。

新建文章时使用 [`assets/TEMPLATE.md`](assets/TEMPLATE.md) 提供的最小文件骨架。它只固定 frontmatter 和 TOC 的位置，不规定章节数量或叙事顺序；根据前面设计的问题链替换所有占位内容。

执行以下命令获取实际时间，不得硬写：

```bash
date '+%Y-%m-%d %H:%M:%S %z'
```

正文包含固定 TOC：

```markdown
1. Table of Contents, ordered
{:toc}
```

### 5. 冷读验收

完稿后至少检查：

1. 只读标题、H2 和每节首句，零上下文读者能否理解全文推进路径；
2. 只读每节的首句和末句，能否直接理解核心问题及解释过程；是否为了过渡而反复设问、绕弯；
3. 逐节检查它是否为回答核心问题所必需，不能仅因“对话里讨论过这个点”就保留；能删而不影响理解的段落应删除；
4. 遮住标题后，读者是否仍能在每项技术正式展开前理解具体问题是什么、原有做法为何不足；正文是否解释了机制与问题的对应关系，而非只改了标题；
5. 是否存在"预备知识"式的前置章节——工具性概念是否在第一个需要它的问题处才引入；
6. 平级 H2 是否超过约 6 个、该归堆的是否已归为大块加小节；
7. 是否仍有问答记录、聊天时间线、无前文指代或答疑式过渡；
8. 每个概念是否在依赖它的内容之前出现；
9. 公式、图、代码和例子是否真正帮助理解，并在首次需要的位置出现；
10. 标题、description、categories、tags 和文件名是否符合 `AGENTS.md`；
11. 中文引号、Markdown 围栏和 LaTeX 分隔符是否正确。

不通过时先重排结构，不要只润色局部句子。

### 6. 预览与发布

按 `AGENTS.md` 执行：本地预览 → 用户确认 → 询问后再 commit/push。用户不满意时继续修改或删除；发布完成后关闭预览服务。
